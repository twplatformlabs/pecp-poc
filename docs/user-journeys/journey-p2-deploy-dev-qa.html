Front-stage actions
  • Runs their own build workflow (using Phase 1 runners) to build the image
  • Pushes the image to the project's JFrog space OPEN Q1
Shared-responsibility line: the team writes and owns the build. The platform provides the JFrog target, creds, and pull config — not the pipeline.
  • Bumps the image reference for dev/qa in the app-of-apps repo
  • Triggers however the team prefers — commit, PR merge, or a CLI helper OPEN Q2
  • Watches Argo pick up the change
  • Sees the workload running in the dev/qa namespace
  • Observes status & logs via Argo and K8s
Back-stage actions
  • JFrog stores the image in the project's isolated space
  • (Xray scanning may run here — feeds later prod evidence) OPEN Q3
  • No platform action — the app-of-apps repo is the team's declarative source
  • Argo (in the nonprod cluster) detects the app-of-apps change and reconciles
  • Pulls the image from JFrog using the injected imagePullSecrets
  • Applies workloads to the target namespace; External Secrets supplies config/secrets
  • Platform engine reflects deployment state as part of the environment's record

Open questions

Q1
JFrog push creds. How build-time push credentials to the project's JFrog space are provided to the team's workflow (and rotated).
Q2
Trigger & manifest bump. Does the platform offer a CLI helper to bump the app-of-apps and deploy (noted as maybe Phase 3/4), or is it entirely the team's own mechanism for now?
Q3
Scan timing. Does Xray/scan run at publish here so the evidence is ready for the prod gate later, or only at promotion time?
Q4
App-of-apps shape. One app-of-apps per project or per team (ties to Flow 1 Q6), and how per-environment paths are structured within it.
Q5
Rollback. Is rollback just a git revert of the app-of-apps, or is there a platform-assisted rollback?

How to read this
Personas are grouped into four planes of the platform operating model. Each card names who they are, what they own, and their role in our first two journeys.
The two journeys
Team Creation — self-service, RBAC-gated. Repo Creation A — individual via github.com, synced. Repo Creation B — team-scoped via platform engine.
One human, many hats
These roles can collapse into a single person — especially on a pilot team, where one individual is the engineering manager, the tech lead, and the application engineer at once. Personas are roles, not people.

Prototyper

AI-first · may not write code at all

Describes what they want in plain language and gets back a working thing on a link they can send to five people. The only persona whose primary surface is the agent rather than GitHub or the CLI — and the only one who need not be an engineer.

Owns / does

  • An engineer wearing this hat can drop into the generated repo; a non-engineer never does

Modeling notes

Compliance posture is a team attribute, not a persona. "Compliant vs non-compliant" forks the AI-capability provisioning step — the team's context decides which kit its repos receive, rather than introducing a separate actor.

Repo creation is two distinct maps. Path A is created on github.com then synced into the platform engine and shown under "my repositories." Path B is created inside the platform engine, tied to a team, with AI capabilities matched to that team's posture.

Producer & Governance mostly sit backstage in these consumer journeys. They become primary actors in their own operator journeys (control-plane build, team deletion, audit exposure) in later phases.

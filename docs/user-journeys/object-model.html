Reading Phase 1

Team is the anchor. Members and team repositories hang off it; the team is the unit of ownership and AI/compliance scope.
Two repo kinds. Team repos (AI + compliance eligible) vs standalone user-owned repos (base only, no team, no AI).
No auto-team. Creating a repo never creates a team; the two are independent acts.

Constants across phases

Platform engine is the record. Not a proxy — the central, up-to-date state across integrated systems (GitHub now; JFrog / K8s / Datadog later).
Both surfaces are valid. GitHub and the platform engine can each originate changes; sync is bidirectional.
Teams bypass Entra. Only Enterprise + org access map to AD groups.
What shifts Repositories move. In Phase 1 repos hang off the Team. In Phase 2 they hang off the Project, which becomes the anchor for all deployment concerns. The Team stays — but Team ↔ Project becomes a many-to-many pairing.

Reading Phase 2

Project is the anchor. Repos, the JFrog space, and the config/secret space hang off it — shared across the project's environments.
Environments are flat. Each gets the same wiring at provision time: namespace, config/secret binding, JFrog pull config, GitOps.
Cluster/account is a detail. Structurally just an environment; the cluster and account it lands in are attributes (prod → prod cluster/account).

Cardinality & open points

Team ↔ Project is many-to-many — a team owns many projects; a project can be run by many teams. Both start 1:1.
Project → Repositories is 1:many — superseding Phase 1's team-owned repo.
Open — JFrog structure, and the unified secret/config store backend (GitHub secrets vs Vault / 1Password).
Proposed

Sandbox — a sibling of Project, not a child

Introduced for the Prototyper. A Sandbox is not a custom environment beneath a Project — it is its own anchor, owned by a person rather than a Team, and it is the only object in the model that deletes itself.
Sandbox · anchor
Making it a custom environment was the tempting shortcut. It fails because a custom environment inherits a Project — and with it a Team owner, a dev/qa/prod triplet, a promotion path and no lifespan. A Sandbox wants none of those.

Nothing here exists yet. The Sandbox object, its TTL and expiry, and the viewer-group enforcement are three of the eight capabilities the Prototyper journey depends on. It is drawn here so the shape can be argued about before it is built.

Reading the Sandbox

It is an anchor, not an environment. Sitting it under a Project would give it an owning Team and a prod sibling — the two things it most needs not to have.
Person-owned is the load-bearing choice. Every other object in the model is owned by a Team. A prototyper may not be on one.
It deletes itself. The only object with a lifespan, which is what stops the prototyping persona becoming a sprawl generator.

Open points

Graduation — how a Sandbox becomes a Project, and what carries across. Undefined, and the sharpest risk: without it, successful prototypes become shadow production.
Viewer group backing — an Entra group, a platform-native list, or something else. Teams deliberately bypass Entra today, which makes reusing it awkward.
Concurrency & entitlement — how many live Sandboxes one person may hold, and whether creating them is part of the alpha grant or separate.

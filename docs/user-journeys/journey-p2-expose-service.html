Front-stage actions
  • Requests exposure via CLI/agent or a manifest for the running service
  • Picks a hostname on the platform default domain (subdomain per env) OPEN Q1
Phase 3: bringing your own domain — the platform would register the domain and its certificate on the consumer's behalf.
  • No action — mesh wiring is applied for them
  • (If opting out of the mesh, requests the exception) OPEN Q3
  • Waits briefly while DNS and the certificate come up
  • Reaches the service externally over HTTPS at its hostname
Back-stage actions
  • Platform engine derives the hostname and validates it against the default domain OPEN Q2
  • Istio gateway + routing configured for the service — mesh mandatory unless opted out OPEN Q3
  • (East-west mTLS raises DR / multi-region questions) OPEN Q5
  • ExternalDNS writes the DNS record OPEN Q4
  • cert-manager issues the certificate via Venafi; auto-renewed for platform-domain hosts
  • Platform engine records the exposure (host, cert, mesh route) on the environment

Open questions

Q1
Hostname derivation. How the host is derived — per service, per namespace, per env? Pattern like <name>.<env>.platform.company.com?
Q2
Default domain. Confirm the platform-owned default domain and how subdomains map to environments.
Q3
Mesh opt-out. Mesh is mandatory — what's the legitimate opt-out path, who approves it, and what does opting out change?
Q4
ExternalDNS approach. The right ExternalDNS setup still needs a proper look — flagged as needing more thought.
Q5
East-west mTLS & DR. Internal mTLS raises disaster-recovery / multi-region questions worth exploring separately.
Q6
BYO domain (Phase 3). When a consumer brings a domain, the platform registers it + its cert — scope and ownership of renewal to be defined.

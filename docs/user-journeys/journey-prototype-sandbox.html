Sandbox

Someone describes what they want in plain language and gets back a working, running thing on a link they can send to five people. The eight platform journeys underneath fire back-stage, in one shot, and the prototyper sees none of them.

Precondition Onboarded, and the MCP catalog exists. The user has an alpha entitlement, and the platform publishes a set of MCP servers the agent can reach and act through, using the user's own credentials. Neither the catalog nor the Sandbox object exists today — see the gap list below.
Read this first This is not a composition of eight journeys — it is one journey with eight things happening underneath. Onboarding, repo creation, CI, project provisioning, environment creation, datastore, exposure and deploy all occur here. If the prototyper experiences any of them as a step, the persona has failed. Front-stage is five stages; everything else is back-stage.

Front-stage actions
  • Describes the prototype in plain language — what it does, who it is for, what it needs
  • Answers the agent's clarifying questions: does it need data? does it need to be signed into? who should be able to see it?
  • Names it and sets a lifespan GAP 3
The only creative step. Everything after this is watching, sharing, or iterating.
  • Watches it being built — no infrastructure choices to make
  • Confirms the human-in-the-loop prompt before anything is provisioned OPEN Q4
Path B wait state: if the prototype needs a datastore, the request routes to a team lead for approval and the flow stops here until someone signs off. This is the one place the prompt-to-link promise breaks. OPEN Q2
  • Nothing — watches progress
  • Receives a link and sends it to a handful of people
  • Adjusts who can open it — adds or removes people over the prototype's life GAP 1
This is the deliverable. Not a repo, not a pipeline — a URL that the right five people can open and nobody else can.
  • Prompts changes in plain language; the agent redeploys
  • Extends the lifespan, or lets it expire GAP 3
  • Asks for it to be graduated into a real project if it proves out GAP 4
Engineer depth (optional)
  • Can point the agent at an existing repo or paste code instead of describing from scratch OPEN Q1
  • Opens the generated repo, reads what the agent wrote, and commits changes directly
  • Can adjust the generated build workflow
  • Inspects build logs and the GitOps repo; can re-run a failed build
  • Same as front-stage — the link is the link
  • Keeps iterating in the repo directly rather than through the agent
Both personas, one flow. The non-engineer never leaves the conversation; the engineer can drop down a level at any stage without changing the journey.
Back-stage actions
  • Agent resolves intent against the MCP server catalog the platform publishes GAP 2
  • Platform validates the user's entitlement to create a sandbox OPEN Q3
  • Acts as the user, with their credentials — entitlement is not widened for the agent
  • Creates the Sandbox object — TTL, group-scoped access, cost cap, no prod environment GAP 3
  • Creates a prototype repo; the agent writes the application code into it
  • Generates a default build workflow — the platform supplies it rather than the team OPEN Q5
  • Provisions the namespace, config/secret binding, JFrog pull config and GitOps wiring
  • Path B: routes the datastore request to the team lead and records the decision as audit
Tension with a stated constant: the shared responsibility model says the platform never owns the build pipeline. Here it generates one. Either this persona is the exception, or the constant needs rewording. OPEN Q5
  • Build runs on the Phase 1 shared runners; image published to the project's JFrog space
  • Argo reconciles into the sandbox namespace
  • No production gate — a sandbox is nonprod by definition and never reaches prod
Why there is no compliance gate here: the gate is a prod admission check. Nothing in this journey targets prod — which is exactly why graduation (GAP 4) matters.
  • Hostname on the platform sandbox domain; Istio route, ExternalDNS record, Venafi certificate
  • Access scoped to the named group — SSO in front, membership enforced at the edge GAP 1
The capability that does not exist. P2·06 exposes a service on the platform default domain with no group scoping — anyone on the network can reach it. “Shareable with a small group” needs an authorization layer the platform does not have.
  • Redeploys on each accepted change
  • Auto-expiry tears down the namespace, datastore, DNS record, certificate and the record itself GAP 3
  • Graduation into a real project — undefined GAP 4
Without expiry and graduation this persona creates sprawl. Anyone can prompt an environment into existence; nothing makes it go away, and nothing turns a good one into a real thing.

What Does Not Exist Yet

8 gaps · the build list for this persona
Every other map in the library describes capabilities that are planned. This one does not. These eight are the things the platform would have to add before this journey is possible at all — ordered by how badly the persona breaks without them.
Gap 1 · blockingGroup-scoped sharing
The whole point of the persona, and it has no home in the model. P2·06 puts a service on the platform default domain — which is reachable by anyone on the corporate network. “Shareable with a small group” needs SSO in front of the prototype plus a membership list the prototyper controls. Without it, “share with five people” is really “publish to the company.”
Blocks the entire value proposition.
Touches H1, H2, H5 in the responsibility model, and adds a new authorization capability.
Gap 2 · blockingMCP server catalog
The agent can only build on this infrastructure if the platform publishes MCP servers it can act through — provisioning, deploying, exposing. Who authors them, who curates the catalog, how the agent discovers them, how they are versioned, and how they authenticate as the user are all undefined. This is arguably a new object in the object model, not just a capability row.
Blocks the AI touchpoint entirely.
Nearest existing thing is the AI capability catalog (K2), which attaches to repos, not to the platform's own actions.
Gap 3 · blockingThe Sandbox object & TTL
Sandbox is not a custom environment. A custom env inherits a project anchor, dev/qa/prod siblings and no lifespan. A Sandbox needs its own rules: a time to live, group-scoped access, a cost cap, no prod sibling, and automatic teardown of everything it created. Reusing E2 would drag in assumptions that actively do not fit.
Without expiry this persona is a sprawl and cost generator.
Touches E2 teardown and E6 cost — both already open.
Gap 4 · highGraduation path
What happens when a prototype is good? Either it becomes a real project — inheriting a proper environment set, the compliance gate and an owning team — or a team rebuilds it from scratch. Nothing in between is safe. Without a defined path, successful prototypes quietly become shadow production: running, depended on, and outside every gate the platform built.
The first question a stakeholder will ask.
Relates to P2·08 Migrate In — the same problem, from inside.
Gap 5 · highSynthetic-data rule
A sandbox with a shareable link and a real datastore is a data-exposure path. The safe position is that sandboxes carry synthetic or seeded data only, never production data — but that has to be a stated and enforced rule, not an assumption. Enforcement is the hard part: nothing stops someone pasting real records into a prototype.
Compliance will raise this whether or not the team does.
Interacts with Gap 1 — the risk is only contained if sharing is genuinely scoped.
Gap 6 · mediumPlatform-generated build
The responsibility model states as a constant that the platform never owns the build pipeline. This persona cannot write one — so either the platform supplies a default build for sandboxes, or the agent generates it on the user's behalf and the user nominally owns it. Both are defensible; the current wording allows neither.
Forces a decision on a stated constant.
Touches C3 build definition, which is currently consumer-only in both phases.
Gap 7 · mediumCost caps & attribution
Anyone who can write a sentence can now provision an environment, a database and a hostname. Multiplied across the organisation, that needs a per-sandbox cost ceiling and attribution back to a person or team. E6 in the responsibility model is entirely undecided — this persona makes it urgent.
Scales badly without a ceiling.
E6 is currently badged undecided.
Gap 8 · mediumPrompt-to-code provenance
The responsibility model says the consumer always owns the application code. When an agent wrote it, that holds legally but weakly in practice. For a sandbox that never leaves nonprod it may not matter — but the moment a prototype graduates, it meets the compliance gate, and “an agent wrote this” becomes a conversation with Compliance about evidence and review.
Only bites on graduation (Gap 4).
Touches B4 application source code and K3 evidence production.

The Sandbox Object & Open Questions

Sandbox — proposed shape

anchor
Owned by a person, not a team. Unlike a Project, a Sandbox belongs to whoever created it — which is what lets a non-engineer have one at all.
lifespan
Has a TTL. Expires by default and must be actively extended. The only object in the model that deletes itself.
access
Carries a viewer group. A membership list the owner controls, enforced at the edge — not a property any other object has.
envs
Exactly one environment, always nonprod. No dev/qa/prod triplet, no promotion path, no compliance gate.
data
Synthetic or seeded only. A datastore is permitted but production data is not.
cost
Capped. A hard ceiling, attributed to the owner.

Open questions

Q1
Starting point. Can the prototyper point the agent at an existing repo, or is every sandbox generated from a blank prompt? Affects whether this is also a “fork and try something” tool.
Q2
The approval wait state. The agent shares the CLI lane, so a datastore needs team-lead sign-off. For a non-engineer with no team lead, who approves? And does a stateless prototype stay genuinely zero-wait?
Q3
Who gets to prototype. Is sandbox creation part of the alpha entitlement, a separate grant, or open to anyone with an account? This decides whether the persona is ten people or ten thousand.
Q4
Human-in-the-loop scope. Promotion to prod requires confirmation. Does provisioning a sandbox, a database, or a public hostname require one too — and how many confirmations before the flow stops feeling conversational?
Q5
Who owns the generated build. Platform-supplied default, or agent-generated and nominally the user's? See Gap 6 — this contradicts a stated constant either way.
Q6
Sandbox domain. Does a sandbox sit on a separate domain from real services, so a link is visibly a prototype rather than mistaken for a product?
Q7
Concurrency. How many live sandboxes may one person hold at once, and what happens at the limit?

What This Journey Consumes

back-stage, invisible to the prototyper
Each of these is a mapped journey in the library. In this flow, none of them is a step the user takes — they are all things that happen while the prototyper waits.

Reused as-is

P1·01
Onboarding — the entitlement precondition, unchanged.
P1·06
CI with GitHub Actions — the runners, though not the authoring (see Gap 6).
P2·05
Deploy to Dev / QA — the GitOps mechanism, targeting the sandbox namespace.
P2·04
Add a Datastore — including its team-lead approval, which is what creates path B.

Reused but altered

P1·05
Team repo via engine — closest existing shape, but the repo here is agent-created and person-owned. P1·02 is the wrong fit: it explicitly carries no AI.
P2·01
Provision project — auto-creates dev, qa and prod. A sandbox wants exactly one nonprod environment and no promotion path.
P2·03
Custom environment — the tempting fit, and the wrong one. See Gap 3.
P2·06
Expose a service — gives a hostname with no group scoping. This is Gap 1, the blocking one.
P2·02
Secrets & config — needed minimally for app config, with a hard rule that no real credentials enter a shareable sandbox.

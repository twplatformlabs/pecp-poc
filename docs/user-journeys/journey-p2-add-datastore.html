Front-stage actions
  • Picks the DB type — DynamoDB or Postgres — and the target environment
  • Chooses the surface: a CLI command, or a K8s manifest in the repo
Lane A · via CLI
  • Submits; the request routes to a team lead for approval
Lane B · via manifest
  • Opens a PR with the manifest; review + merge is the approval
The asymmetry: CLI needs a team-lead sign-off because it leaves no git trail; the manifest is self-service because the PR history is the audit artifact.
  • Watches provisioning — no manual AWS steps
  • Runs a read command (CLI/agent) to fetch connection details, or the app consumes them from the namespace
  • Connects the app to the database
Back-stage actions
  • Platform engine confirms the user's rights on the project/environment
  • Prepares provisioning for the chosen type + env
  • Lane A: platform engine routes approval to the team lead and records the decision as audit
  • Lane B: git history + PR provide the audit trail; no separate approval step OPEN Q5
  • Lane A: platform engine provisions a new AWS DB, tied to the environment
  • Lane B: a Crossplane (or custom) operator reconciles the manifest → provisions the AWS DB OPEN Q2
  • Both converge on the same DB tied to the env OPEN Q3
  • Connection details written to the unified secret/config store
  • Synced in-cluster via External Secrets as a K8s Secret OPEN Q6
  • Teardown when the environment is deleted OPEN Q4

Open questions

Q1 ✓
Resolved — provision, not connect. The CLI provisions a new DB (not a connect-to-existing), and the read command fetches its details from the store.
Q2
Operator choice. Crossplane vs a custom operator for the manifest lane.
Q3
Lane convergence. Confirm both lanes converge on the same provisioning + same store landing (intended for now), rather than two divergent implementations.
Q4
Teardown & prod DBs. Teardown on env delete — with a guardrail against dropping a DB with data? And prod DB static-stability / multi-AZ per the account-topology ADR.
Q5
Approval logic. Confirm the trigger: CLI → team-lead approval; manifest → self-service. Any exceptions (e.g. prod DBs always need approval)?
Q6
ESO wiring. How connection secrets flow through External Secrets — depends on the secret-store backend decision (Flow 2 Q1).
Q7
DB types. DynamoDB + Postgres to start — what's the roadmap for additional engines?

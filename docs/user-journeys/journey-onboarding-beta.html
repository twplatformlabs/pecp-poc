Front-stage actions
  • Mostly done to the user at this stage
  • (Optional) expresses interest in joining the platform beta OPEN Q1
  • No visible action — provisioning happens behind the scenes
  • Receives a welcome email: how to reach GitHub & the platform engine, and what beta includes
  • Clicks through the links
  • Logs into the platform engine; sees beta status and what it unlocks
  • Sees "my repositories" (empty to start)
  • Reviews the shared-responsibility model — what's in vs out of scope
  • Chooses what to create: a user-owned repo, or a team (then team-owned repos)
  • Picks the surface: start in GitHub, or start in the platform engine
Launchpad: this stage hands off to the four creation flows (2×2 below). A beta user who creates a team can assign users/admins and own team repos.
Back-stage actions
  • Platform team / Product Owner selects the user into the beta cohort
  • An RBAC entitlement is created granting beta rights (incl. team creation) OPEN Q3
  • User is added to the core AD / Entra group → inner-source org access
  • Granted GitHub Enterprise access OPEN Q4
  • Platform engine records the beta entitlement against the user
  • SSH key set up so the user can clone later OPEN Q5
  • Platform engine sends the onboarding email with access details + a capability overview
  • Platform engine renders the user's entitlements, capability catalog, and docs
  • Shared-responsibility model lists out-of-scope items: CI/CD, secrets, observability, deploy envs
  • Platform engine routes the user to the matching creation flow
  • Both GitHub-initiated and control-plane-initiated paths sync bidirectionally

Open questions

Q1
Nomination. Do beta users self-nominate / request in, or does the platform team hand-pick them? Is there an approval step, and who owns it — Platform Product Owner?
Q2
Prior access. Does the existing employee already have GitHub Enterprise access, or does beta enrollment grant it for the first time?
Q3
Entitlement scope. What exactly does beta unlock — is team creation gated to beta users only in Phase 1? What's the backing RBAC model?
Q4
Access level. GitHub Enterprise read, org write — confirm. What repo-level permission does a creator get by default?
Q5
SSH provisioning. When/where in onboarding does the user's SSH key get set up, so cloning works later? (Connects to the SSH-vs-PAT question.)

Related flows — not this map

Onboarding — New Employee out of scope · later
HR-triggered: an HR event → platform engine hook → auto-provision AD group + GitHub. This is what was mistakenly placed on the front of Repo Path A — it belongs here as a sibling map, and is not Phase 1 or 2.
Team — created in GitHub reconcile
Is an explicit Team-in-GitHub creation the same as the earlier auto-team-via-webhook side-effect (a solo repo creator gets dropped into a team), or two different things? This decides whether "team from GitHub" is a first-class path or just a fallback.

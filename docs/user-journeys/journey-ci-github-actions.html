CI with GitHub Actions

After a repo exists, a developer adds a GitHub Actions workflow that runs on a shared runner. CI compute is bundled with repo access — the platform engine is not involved.

Precondition A repo exists (from Flow 2 or Flow 5) and the user has access to it. Runner access is bundled with that repo access.
Note The platform engine does nothing here in Phase 1. Runners are basic and shared — you simply get them with repo access. Surfacing availability via pe-cli status gh runners is a later idea (see Phase 2 preview below).

Open questions

Q1
Runner type & default. Are the basic runners GitHub-hosted, a self-hosted pool, or labelled sets? What's the default runner label a user gets without choosing?
Q2
Documentation home. Where exactly does the org main page surface available runners, and who keeps that list current?
Q3
Limits & sharing. Any concurrency limits, quotas, or cost/allocation in Phase 1? Runners shared org-wide — is contention a concern?
Q4
Boundary check. Confirm the platform engine genuinely does nothing for runners in Phase 1 — no registration, no audit capture on runner usage.
